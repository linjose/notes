分散式 GPU 技術與開源生態系：架構、專案分層及整合方案
一、前言
隨著大型語言模型（Large Language Models, LLM）、多模態人工智慧及 AI Agent 應用快速發展，AI 系統的運算需求已從單一 GPU 的模型推論，逐步延伸至多 GPU、多伺服器及大型運算叢集的協同執行。

在這個發展過程中，分散式 GPU（Distributed GPU Computing） 成為建構高效能、可擴展 AI 基礎設施的重要技術。其核心不只是增加 GPU 數量，而是透過模型平行化、推論服務分流、工作排程及資源管理等機制，讓多個運算資源能夠有效協作。

目前開源生態系已發展出多種技術，包括 Ray、vLLM、SGLang、NVIDIA Dynamo、DeepSpeed、Kubernetes、Volcano、Kueue 及 HAMi 等。這些專案的功能並不完全相同，有些負責模型推論，有些負責分散式工作執行，另一些則負責叢集部署與 GPU 資源管理。

因此，理解分散式 GPU 技術的關鍵，不只是比較個別專案的效能，而是釐清各專案在整體架構中的定位、相互依賴關係，以及哪些組合適合用於實際部署。
二、分散式 GPU 的基本概念
2.1 什麼是分散式 GPU？
分散式 GPU 是指透過軟體框架、通訊機制與資源管理系統，整合多張 GPU 的運算能力，完成單一 GPU 難以有效處理的工作，或共同承擔大量 AI 運算需求。

依據 GPU 的配置方式，可分為三種主要模式。









（一）單機多 GPU

多張 GPU 安裝在同一台伺服器內，可以透過 PCIe、NVLink 等互連技術交換資料。適合大型模型切分、張量平行與單機高吞吐量推論。












（二）跨主機多 GPU

多台伺服器透過高速網路連接，分工執行同一模型或同一工作。適合超出單機記憶體容量的大型模型，以及需要多機協同的推論服務。












（三）分散式推論服務

每台伺服器可以執行完整模型，透過請求路由將不同使用者的工作分配至不同副本。適合大量並行使用者、企業 AI 服務及多租戶環境。



這三種模式可以單獨使用，也可以組合。例如，一個大型模型可先分散至單台伺服器的多張 GPU，再將多個模型副本部署到不同伺服器，最後透過服務路由分配請求。
2.2 分散式 GPU 解決哪些問題？
技術需求	主要解決方式
模型無法放入單張 GPU 記憶體	模型平行化、張量平行、流水線平行
同時有大量使用者呼叫模型	增加推論副本、批次處理、請求路由
大量 AI 任務需要同時執行	分散式工作調度與平行運算
多個團隊共用 GPU 叢集	資源配額、排程、GPU 切分與隔離
推論工作需要高可用性與彈性擴展	容器編排、服務健康管理與自動擴縮

需要特別注意，分散式 GPU 不一定能讓單一請求更快完成。跨主機通訊會帶來額外延遲，且需要高速網路、適當的平行化策略與負載配置。若只是處理少量請求，單機推論往往更簡單且具成本效益。
三、分散式 GPU 的軟體架構分層
分散式 GPU 的開源軟體並非單一框架可以完整涵蓋，而是由不同層次的技術共同組成。以下以 AI 推論服務為核心，將相關專案整理成五個邏輯層級。
第 5 層：應用與 AI 工作流程
RAG、AI Agent、企業 API、批次文件處理


第 4 層：分散式工作與推論服務編排
Ray Serve LLM、Ray Core、NVIDIA Dynamo


第 3 層：模型推論與平行化
vLLM、SGLang、DeepSpeed


第 2 層：叢集編排與資源管理
Kubernetes、Kueue、Volcano、HAMi


第 1 層：硬體、驅動與通訊
GPU、CUDA／ROCm、NCCL／RCCL、高速網路

圖示為功能上的邏輯分層，不代表每個專案都必須安裝在獨立層級，或只能與相鄰層整合。

3.1 第一層：硬體與 GPU 通訊
這一層是整個系統的運算基礎，包含 GPU、驅動程式、GPU 運算環境，以及跨 GPU 的通訊機制。

主要元件包括：
- CUDA： NVIDIA GPU 的運算平台。
- ROCm： AMD GPU 的運算軟體平台。
- NCCL／RCCL： 分別用於 NVIDIA／AMD GPU 的集合通訊，例如 All-Reduce。
- 高速互連： PCIe、NVLink、InfiniBand 或 RoCE 等，影響跨 GPU、跨伺服器交換資料的效率。
這一層決定分散式執行的效能上限。即使軟體支援多台 GPU，如果網路頻寬不足或延遲過高，跨主機推論仍可能受到嚴重影響。
3.2 第二層：叢集編排與 GPU 資源管理
這一層主要解決「有哪些機器、哪些 GPU 可用，以及工作應該部署在哪裡」的問題。
- Kubernetes： 管理容器、節點、服務部署及故障恢復。
- Kueue： 在 Kubernetes 上管理工作佇列、資源配額與工作啟動時機。
- Volcano： 針對批次運算、AI／HPC 工作等提供進階排程能力。
- HAMi： 提供 GPU 虛擬化、切分與共享等能力，實際支援程度依 GPU 型號及配置而異。
Kubernetes、Kueue 與 Volcano 並不是三個互相替代的 GPU 推論引擎。Kueue 側重工作准入與配額，Volcano 側重批次與成組工作排程；是否同時部署，應依既有排程器、工作負載與管理需求決定。

3.4 第四層：分散式執行與推論服務編排
這一層是整體架構的協調者，負責決定工作如何執行、模型如何分配，以及請求如何送往適當的推論工作節點。

Ray 是通用的分散式運算框架；Ray Serve LLM 則進一步針對大型語言模型提供服務部署、擴縮與多機推論能力。

NVIDIA Dynamo 則聚焦於大型生成式 AI 推論服務，提供請求路由、KV Cache 管理、Prefill／Decode 分離等能力，並能整合 vLLM、SGLang 等推論引擎。

這一層有兩個重要觀念：
1. Ray 與 vLLM 並非競爭關係。Ray 可以負責跨主機工作執行，而 vLLM 負責模型推論。
2. Ray Serve LLM 與 NVIDIA Dynamo 都能處理分散式推論服務問題，但兩者的架構與功能有所重疊，通常應先選擇其中一個作為主要服務編排方案，再評估是否有必要引入另一個。
3.5 第五層：應用與 AI 工作流程
最上層是使用者實際接觸的服務，例如 RAG 知識庫、AI Agent、程式碼助理、醫療文件分析與企業 API。

這一層不一定需要直接操作 GPU。應用程式可以透過 OpenAI 相容 API 或其他服務介面呼叫底層推論服務，由下層負責 GPU 配置與運算。

若應用程式需要同時執行網路搜尋、文件解析、資料庫查詢與多次模型呼叫，Ray 可以用來協調這些工作；若只需要呼叫單一模型 API，則不一定需要導入 Ray。

四、主要專案之間的整合關係
理解各層功能後，下一個重要問題是：哪些專案組合已經有明確的官方支援或整合路徑？
4.1 整合成熟度的判斷原則
本文將整合關係分為三類：
- A 類：官方文件直接支援。 有明確的使用指南、設定方式或部署流程。
- B 類：有標準介面或生態系整合。 可以整合，但仍須驗證版本、硬體與功能相容性。
- C 類：需要自行開發或驗證。 不宜只因為各專案都是開源，就假設可以直接組合。
這是依據官方文件與專案定位所作的工程判斷，並非所有版本、所有硬體組合的完整相容性認證。

六、導入時應注意的技術問題
分散式 GPU 不只是安裝幾個開源套件，還需要評估以下因素：
1. GPU 記憶體容量： 模型權重、KV Cache、批次大小及上下文長度都會影響 GPU 記憶體需求。
2. GPU 互連與網路： 跨主機模型平行通常比單機多 GPU 更依賴高速、低延遲的網路。
3. 模型平行化策略： 張量平行、流水線平行與資料平行分別解決不同問題，不宜只依 GPU 數量決定。
4. 資源管理責任： 應區分推論引擎內部的 GPU 配置、Ray 的工作資源調度，以及 Kubernetes 的節點與容器管理。
5. 監控與故障處理： 除了 GPU 使用率，也應監控每秒 Token 數、首 Token 延遲、請求佇列、GPU 記憶體與跨節點通訊狀況。
尤其要注意，Kubernetes 的 GPU 排程不等於 GPU 切分。標準 Kubernetes 可透過裝置外掛將 GPU 作為可排程資源；若需要更細緻的共享或虛擬化，才進一步評估 HAMi、MIG 或其他符合硬體條件的機制。

七、結論與建議
分散式 GPU 的開源生態系可歸納為三個核心方向：
- 模型推論效能： vLLM、SGLang、DeepSpeed。
- 分散式工作與推論服務： Ray、Ray Serve LLM、NVIDIA Dynamo。
- 叢集與 GPU 資源管理： Kubernetes、Kueue、Volcano、HAMi。
建議依照需求採取漸進式導入策略：
- 若目標是研究大型模型如何跨多張 GPU 執行，從 vLLM + Ray 開始。
- 若目標是建構可擴展的分散式推論服務，研究 Ray Serve LLM + vLLM／SGLang。
- 若目標是大型 GPU 叢集的高效能生成式 AI 推論，評估 NVIDIA Dynamo + vLLM／SGLang。
- 若目標是建置組織共用的 GPU 資源平台，再導入 Kubernetes，並依需求選擇 Kueue、Volcano 或 HAMi。
最重要的原則是：先確定要解決的是模型容量、推論吞吐量、工作平行化，還是 GPU 資源共享，再選擇相對應的開源專案。 如此才能避免架構過度複雜，也更容易建立可維運、可擴展的 AI 推論平台。
