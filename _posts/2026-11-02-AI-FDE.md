# FDE 如何與 AI 協作，發揮最大的價值？

## 從工程師到問題解決者：建立以 AI 為核心的全流程交付能力

### 一、前言：AI 時代，工程師的價值正在重新定義

過去，軟體工程師的核心價值在於掌握程式語言、熟悉開發框架、理解系統架構，以及具備解決技術問題的能力。一個工程師能夠寫多少程式碼、完成多少功能，往往是衡量其技術能力的重要指標。

然而，生成式 AI 的出現，正在改變這套價值體系。

當 AI 已經能夠協助工程師撰寫程式碼、產生測試案例、分析錯誤、設計資料庫，甚至規劃系統架構時，單純以程式碼產出量衡量工程師的生產力，已經逐漸失去意義。

真正的差異，不再只是誰寫程式寫得比較快，而是誰能夠更有效地理解問題、整合技術、驗證成果，並將需求轉化為真正可以使用的產品。

這也是 FDE（Forward Deployed Engineer，前線部署工程師）在 AI 時代特別值得重視的原因。

FDE 並不是單純的軟體工程師，也不是傳統的系統分析師或技術顧問，而是一種結合工程實作、場域理解、產品思維與問題解決能力的角色。

當 FDE 與 AI 建立有效的協作模式時，其價值將不只是提升個人開發效率，而是有機會重新定義整個軟體開發與產業數位轉型的工作方式。

### 二、FDE 的核心精神：從交付功能轉向解決問題

傳統軟體開發通常有一套相對明確的流程：

1. 業務單位提出需求。
2. PM 或系統分析師整理需求。
3. 工程師進行系統設計。
4. 開發團隊撰寫程式。
5. 測試團隊進行驗證。
6. 專案團隊交付系統。

這種模式的優點是分工清楚，但也容易產生問題：需求與技術實作之間存在多層溝通，工程師未必真正理解使用者的問題，而 PM 也未必能夠完整掌握技術實作的限制。

FDE 的工作方式則有所不同。

FDE 強調直接進入客戶或使用者的實際場域，理解問題發生的情境，並且透過工程能力快速建立解決方案。

例如，當一家醫院希望導入 AI 時，傳統的開發模式可能先從需求訪談、規格書、系統建置開始。

但 FDE 會先思考：

- 醫護人員真正遇到的問題是什麼？
- 現有系統為什麼無法解決？
- 哪些資料可以取得？資料品質如何？
- AI 是否真的適合解決這個問題？
- 能否先做出一個小型原型，讓使用者實際操作？
- 如何透過使用者回饋快速修正？

FDE 不會將需求文件視為工作的終點，而是把真正解決問題視為工作的起點。

FDE 的核心價值，是縮短問題發現、技術實作與實際價值產生之間的距離。

而 AI 的加入，恰好能夠大幅放大這種工作模式的效益。

### 三、FDE 與 AI 協作的五個關鍵能力

要讓 FDE 與 AI 協作發揮最大效果，不能只是把 AI 當成程式碼產生器，而應該將 AI 視為一個可以共同思考、共同開發、共同驗證的工程夥伴。

我認為可以從五個層次建立協作模式。

#### 1. 問題定義：由 FDE 掌握場域，AI 協助分析

FDE 最重要的能力之一，是理解真實世界的問題。

AI 雖然可以分析大量文件、整理訪談紀錄、比較不同解決方案，但它並不一定知道使用者真正的痛點，也不一定能理解組織內部的權責關係、工作習慣與隱性限制。

因此，這個階段應由 FDE 主導。

FDE 負責：

- 進入實際場域，觀察工作流程。
- 與使用者溝通，釐清真正的問題。
- 判斷需求的優先順序。
- 確認技術、預算、法規及組織限制。

AI 負責：

- 整理訪談紀錄與需求文件。
- 分析問題之間的關聯。
- 提出可能的解決方案。
- 協助建立 User Story、流程圖及系統規格。
- 找出需求中尚未被考慮的風險。

這種分工可以讓 FDE 將更多時間放在理解問題，而不是花費大量時間整理文件。

#### 2. 系統設計：由 FDE 決策，AI 擔任架構顧問

當問題被定義之後，下一步就是將問題轉化為技術方案。

這個階段，AI 可以扮演非常有價值的技術顧問。

例如，FDE 可以要求 AI：

- 比較不同開源框架的適用性。
- 設計前後端與資料庫架構。
- 評估 API 與資料交換方式。
- 規劃 RAG、Agent 或 Graph RAG 架構。
- 分析系統部署成本及效能瓶頸。
- 評估既有系統整合的可行性。

但必須注意，AI 提出的架構不代表一定正確。

FDE 必須理解技術選擇背後的取捨，例如可維護性、擴充性、安全性、效能、部署環境及長期營運成本。

尤其在企業與政府專案中，能夠運作的系統不一定是能夠長期維運的系統。

因此，最有效的協作方式是：

AI 提供多種可能性，FDE 負責技術判斷與架構決策。

#### 3. 快速實作：讓 AI 成為主要的開發加速器

這是目前 AI 最容易產生直接效益的環節。

FDE 可以運用 AI Coding Agent，將原本需要數天甚至數週的工作，縮短至數小時或數天。

包括：

- 建立前端介面與互動功能。
- 撰寫後端 API。
- 設計資料庫 Schema。
- 建立資料匯入及轉換程序。
- 整合開源專案與第三方服務。
- 撰寫自動化部署腳本。
- 建立測試程式與技術文件。

在這個階段，FDE 不需要親自撰寫每一行程式碼，而是應該具備拆解任務、提供上下文、分配工作、檢查成果及整合程式碼的能力。

例如，可以讓不同 AI Agent 分別負責：

| AI Agent            | 工作任務      |
| ------------------- | --------- |
| Architect Agent     | 系統架構與技術方案 |
| Frontend Agent      | 前端介面及互動   |
| Backend Agent       | API 與商業邏輯 |
| Database Agent      | 資料庫設計與查詢  |
| Testing Agent       | 測試案例及品質驗證 |
| Documentation Agent | 文件與部署說明   |

FDE 則扮演整體技術負責人，確保各個模組能夠正確整合。

這種模式的重點不是讓 AI Agent 越多越好，而是讓每個 Agent 都有明確的責任範圍、輸入條件及交付標準。

#### 4. 品質驗證：AI 產生的程式碼必須經過工程化驗證

這是 FDE 與 AI 協作時最容易被忽略，卻也是最重要的環節之一。

AI 可以非常快速地產生程式碼，但程式碼能夠執行，不代表系統就具備品質。

常見問題包括：

- 功能看似正常，但特殊情境下發生錯誤。
- API 回傳格式不一致。
- 資料庫交易處理不完整。
- 權限控管存在漏洞。
- 程式碼重複或架構不一致。
- 修改一個模組卻影響其他功能。
- 測試案例只驗證正常情境，忽略例外情境。

因此，FDE 必須建立一套 AI 輔助的品質管理流程。

建議至少包含：

| 驗證層次    | 驗證方式                                       |
| ------- | ------------------------------------------ |
| 程式碼品質   | Lint、Static Analysis、Code Review           |
| 功能正確性   | Unit Test、Integration Test                 |
| 系統效能    | Load Test、Stress Test                      |
| 資安      | SAST、DAST、Dependency Scanning              |
| AI 回應品質 | Evaluation、Ground Truth、Hallucination Test |
| 部署品質    | CI/CD、Rollback、Monitoring                  |

其中非常重要的一點，是讓 AI 不只負責撰寫程式，也要負責檢查自己的成果，甚至由不同 Agent 進行交叉審查。

不過，不能只依賴 AI 自我檢查。對於重要系統，仍應透過自動化測試、獨立審查及人工驗收建立可信賴的品質保證。

AI 負責加速產出，工程流程負責確保品質，FDE 負責承擔技術判斷與交付責任。

#### 5. 持續改善：從一次性專案走向持續演進

傳統專案經常以驗收、結案作為工作的終點。

但 FDE 的價值不應只停留在交付系統，而是持續觀察系統在真實場域的表現。

例如：

- 使用者是否真的願意使用？
- 系統是否縮短工作時間？
- AI 回答是否符合實際需求？
- 哪些功能使用頻率最高？
- 哪些錯誤反覆發生？
- 是否有新的流程可以自動化？

AI 可以持續協助分析 Log、使用者回饋、錯誤紀錄與效能資料，提出改善建議。

FDE 則根據實際使用情況決定下一輪開發方向。

如此一來，系統不再只是一次性交付的軟體，而是能夠持續學習、調整及改善的產品。

### 四、FDE + AI 的最佳工作模式：人類負責方向，AI 負責執行，人類負責驗證

如果將上述五個階段整合，可以形成一個完整的協作循環。

## FDE × AI 協作循環

## 1. Understand

理解問題與場域

FDE 主導，AI 協助整理與分析

## 2. Design

設計解決方案

FDE 決策，AI 提供架構與技術建議

## 3. Build

快速開發與整合

AI Agent 執行，FDE 協調與整合

## 4. Verify

測試與品質驗證

AI 協助測試，FDE 確認品質與風險

## 5. Deploy & Improve

部署、觀察與持續改善

FDE 與 AI 根據真實回饋持續迭代

回到問題定義，形成持續改善循環

這套模式最重要的觀念是：FDE 不應該成為 AI 的操作員，而應該成為 AI 協作團隊的技術領導者。

他的工作不是把每一個指令都交給 AI，而是知道什麼問題值得解決、如何拆解問題、如何分配工作，以及如何判斷最終成果是否真正符合需求。

### 五、從個人 FDE 到 AI Engineering Team：建立多 Agent 協作組織

當 AI 能夠承擔越來越多的工程工作時，FDE 的角色也會從個人開發者逐漸轉變為 AI Engineering Team 的協調者。

這裡可以進一步思考一個新的組織型態：

一位 FDE + 多個專業 AI Agent + 必要的人類專家。

例如，假設要協助一家醫院導入 AI 病歷摘要系統：

FDE / Technical Lead

場域理解、任務分配、架構決策、成果交付

Domain Agent

醫療流程與需求分析

Development Agent

前後端程式開發

Data Agent

FHIR、資料整合與 RAG

QA / Security Agent

測試、資安與品質驗證

醫院實際應用場域

醫師、護理師、資訊室及實際使用者

這樣的架構有幾個優勢：

第一，工程工作可以平行化。不同 Agent 可以同時處理前端、後端、資料整合與測試工作。

第二，專業知識可以模組化。不同 Agent 可以依據各自的知識庫、規範及任務指令執行工作。

第三，FDE 可以將注意力集中在高價值工作，例如場域溝通、系統整合、技術決策與成果驗收。

但必須注意，多 Agent 並不代表可以完全無人管理。Agent 之間需要有明確的任務介面、共享的規格、程式碼版本管理、權限限制及交付驗收機制。否則 Agent 越多，反而可能造成重複工作、互相覆寫及整合成本增加。

### 六、FDE 應該具備什麼樣的 AI 工程環境？

如果要讓上述工作模式真正落地，不能只依賴 ChatGPT 或單一 AI Coding 工具，而應該建立完整的 AI Engineering Environment。

可以分成以下幾個層次：

| 技術層次                       | 代表工具或專案                         | 主要用途           |
| -------------------------- | ------------------------------- | -------------- |
| AI Model                   | GPT、Claude、Qwen                 | 推理、分析、程式生成     |
| AI Coding                  | Claude Code、Codex、OpenHands     | 程式開發與修改        |
| Agent Orchestration        | LangGraph、CrewAI                | 任務拆解與 Agent 協作 |
| Execution Environment      | Docker、Kubernetes               | 隔離執行與部署        |
| Knowledge & Memory         | PostgreSQL、pgvector、Apache AGE  | 專案知識、上下文與關聯    |
| Development Infrastructure | Git、GitHub、CI/CD                | 版本管理與自動化       |
| Quality & Observability    | pytest、Playwright、OpenTelemetry | 測試、追蹤與監控       |

其中值得特別強調的是，FDE 應該逐漸建立自己的 Project Context。

每個專案都應該具有：

- 專案目標與需求規格。
- 系統架構與技術決策紀錄。
- API 與資料庫定義。
- 開發規範與 Coding Standards。
- 測試案例與驗收標準。
- 已知問題及風險紀錄。
- 部署與維運文件。

這些資料不只是給工程師閱讀，更是提供 AI Agent 穩定工作的上下文。

當 AI 能夠持續理解專案的架構、歷史決策與開發規範，就不必每次開啟新的工作階段，都重新解釋整個專案。

這也是從單純使用 AI 工具，進一步走向 AI-Native Engineering 的重要一步。

### 七、FDE 時代，工程師需要重新培養哪些能力？

AI 不會讓工程師失去價值，但會重新分配工程師的價值。

未來 FDE 的能力組合，可能會從傳統的技術專業，轉向以下六個面向：

| 核心能力                 | 重要性 | 說明                 |
| -------------------- | --- | ------------------ |
| Problem Solving      | 極高  | 能否找到真正值得解決的問題      |
| Domain Knowledge     | 極高  | 能否理解產業與實際場域        |
| System Thinking      | 極高  | 能否設計完整且可維運的系統      |
| AI Orchestration     | 極高  | 能否有效分配與管理 AI Agent |
| Engineering Judgment | 極高  | 能否判斷程式碼與技術方案的品質    |
| Communication        | 高   | 能否與使用者及跨領域團隊合作     |

這也代表，未來優秀的 FDE 不一定是最擅長某一種程式語言的人，而是能夠將不同技術、不同專業及不同資源整合起來，快速解決實際問題的人。

當然，這不代表工程師可以完全不懂程式。

相反地，AI 越能夠產生程式碼，工程師越需要具備閱讀、理解、除錯、架構設計與驗證程式碼的能力。

因為如果無法判斷 AI 的產出是否正確，就很難真正掌握系統。

### 八、結論：AI 時代最有價值的工程師，是能夠帶領 AI 解決真實問題的人

FDE 的興起，反映出軟體工程正在從以程式碼為中心，逐漸轉向以問題解決與價值交付為中心。

過去，工程師必須花費大量時間處理程式碼撰寫、文件整理、測試及系統整合等工作。

現在，AI 已經能夠承擔其中相當大一部分的工作。

因此，工程師應該重新思考自己的角色：不是與 AI 比較誰寫程式比較快，而是透過 AI 擴大自己的問題解決能力。

我認為，未來最具競爭力的 FDE，應該具備以下三個特質：

第一，懂得走進場域。 不只是等待需求，而是能夠理解使用者真正的問題，找到值得解決的事情。

第二，懂得運用 AI。 不只是使用 AI 工具，而是能夠設計工作流程、管理多個 Agent，將 AI 變成一支可以協作的工程團隊。

第三，懂得對成果負責。 不只是讓程式成功執行，而是確保系統安全、可靠、可維護，並且真正產生使用價值。

從這個角度來看，FDE 並不是 AI 時代的一種新職稱而已，而是一種新的工程工作方法。

它將場域理解、工程能力、AI 協作與產品交付整合在一起，讓原本需要多個角色、多個部門才能完成的工作，有機會透過小型高效團隊快速完成。

未來的工程生產力，不再只是計算一個工程師一天能寫多少行程式碼，而是衡量一個工程師能夠帶領多少 AI 能力，解決多少真實世界的問題，創造多少實際價值。

這或許就是 AI 時代 FDE 最值得期待的地方。

## 延伸思考：組織如何導入 FDE + AI？

如果將這篇文章進一步應用到企業、研究法人或政府機構，我認為有一個值得嘗試的方向：

將 FDE 作為 AI 導入與產業轉型的核心執行角色，而不是再增加一層 PM 或 AI 顧問。

尤其在產業 AI 化的過程中，企業真正缺少的往往不是 AI 技術介紹，而是能夠理解產業問題、掌握技術、快速開發原型，並且將 AI 導入日常工作流程的人。

可以建立三層組織模式：

1. Domain Team： 提供產業知識、場域需求與實際問題。
2. FDE Team： 負責需求轉譯、技術整合、AI 協作及產品交付。
3. AI Engineering Platform： 提供模型、Agent、開發環境、知識庫、測試及部署基礎設施。

這樣才能形成可複製、可擴充的 AI 導入能力，而不是每次遇到新的產業需求，就重新成立一個專案團隊。

我認為這個方向也可以用一句話概括：

AI 產業化需要打造 AI 產品，產業 AI 化則需要培養能夠帶著 AI 進入產業、解決問題的 FDE。
